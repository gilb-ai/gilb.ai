# Чек-лист из 23 пунктов

У каждого пункта: требование, где искать, что считать провалом и что можно
проверить только в панели сервиса.

## Дизайн и производительность

**1. Единая дизайн-система.** Один документ/файл токенов, которому соответствуют
все цвета, размеры шрифтов и отступы.
- Искать: `tailwind.config.*`, `theme.*`, CSS-переменные в `:root`, `DESIGN.md`.
- Провал: захардкоженные `#hex`/`rgb()`, `px`-размеры шрифтов и отступов в
  компонентах мимо токенов (`grep -rnE '#[0-9a-fA-F]{3,6}\b|font-size:\s*[0-9]+px'`),
  произвольные классы Tailwind вида `text-[13px]`, `bg-[#…]`.

**2. Состояния экранов.** Для каждого экрана с данными есть загрузка, пустое
состояние и ошибка.
- Искать: компоненты, которые делают `fetch`/`useQuery`/`supabase.from(…)`.
- Провал: рендер только при успехе; нет веток `isLoading`/`error`/`length === 0`;
  `catch` с одним `console.log`.

**20. Нестандартный ввод.** Имена с апострофами (O'Brien), эмодзи, текст справа
налево (арабский, иврит) не ломают поля ввода.
- Искать: валидацию имён (`/^[a-zA-Z]+$/` — провал), ручную сборку SQL строками
  (провал), `.length` для лимитов с эмодзи, отсутствие `dir="auto"` на полях
  пользовательского текста, `escape`/`dangerouslySetInnerHTML`.

**21. Изображения.** Форматы WebP/AVIF; всё ниже первого экрана — `loading="lazy"`.
- Искать: `*.png|*.jpg` в `public/`/`assets/`, теги `<img>` без `loading="lazy"`,
  использование `next/image` или аналога.

**22. Индексы.** На полях, по которым чаще всего фильтруют и сортируют, есть индексы.
- Искать: `.eq()`, `.order()`, `WHERE`, `ORDER BY`, внешние ключи в запросах;
  `CREATE INDEX` в миграциях. Внешние ключи в Postgres не индексируются автоматически.
- Провал: часто фильтруемый столбец (`user_id`, `created_at`, `status`) без индекса.

## Безопасность

**3. Приватные ключи только на сервере.** Фронтенд и вся история Git чистые;
когда-либо раскрытые ключи заменены.
- Искать: переменные с публичными префиксами (`NEXT_PUBLIC_`, `VITE_`,
  `REACT_APP_`, `EXPO_PUBLIC_`), содержащие секреты; `service_role`, `sk_live_`,
  `sk_test_`, `whsec_`, ключи OpenAI/Anthropic в клиентском коде.
- История: `git log -p --all -S 'sk_live' `, `git log --all --diff-filter=A -- '*.env*'`;
  если доступен — `gitleaks detect` или `trufflehog git file://.` (только чтение).
- Замену ключей в репозитории не проверить → «Требуется моё подтверждение»
  со списком ключей, которые нужно перевыпустить.

**4. Авторизация на сервере и RLS.** Каждый эндпоинт сам проверяет, кто пользователь
и есть ли у него права; в базе включена RLS.
- Искать: API-роуты, серверные функции, edge functions — проверка сессии в начале
  и проверка владельца ресурса (`where user_id = auth.uid()`).
- В миграциях: `ENABLE ROW LEVEL SECURITY` для каждой таблицы, политики не вида
  `using (true)` для чувствительных данных.
- Провал: доверие `userId` из тела запроса; использование `service_role` там, где
  хватает ключа пользователя; таблица без RLS.
- Панель: Supabase → Table Editor / Authentication → Policies — у каждой таблицы RLS enabled.

## Платежи

**6. Вебхуки.** Подпись проверяется; повторная доставка того же события не
засчитывается дважды.
- Искать: обработчик вебхука — `stripe.webhooks.constructEvent` (или аналог) на
  **сыром** теле запроса; сохранение `event.id` с уникальным индексом или
  upsert по идентификатору платежа.
- Провал: `JSON.parse` тела без проверки подписи; инсерт без защиты от дублей.

**7. Возвраты, отмены, неудачные списания.** Каждый сценарий обрабатывается один
раз и выставляет правильный статус.
- Искать: обработку `charge.refunded`, `customer.subscription.deleted`,
  `invoice.payment_failed`, `payment_intent.payment_failed` (или аналогов).
- Прогон: только в тестовом режиме (`stripe trigger …` с тестовым ключом), если
  он есть локально; иначе — «Требуется моё подтверждение» с инструкцией.

**8. Окончание пробного периода и подписки.** Доступ отзывается вовремя.
- Искать: где проверяется доступ — по статусу/дате окончания с сервера, а не по
  флагу в клиенте; обработку `customer.subscription.updated/deleted`,
  `trial_will_end`.
- Провал: доступ выдаётся навсегда после первой оплаты; проверка только на фронтенде.

**9. Переход из теста в прод.** Рабочие ключи и секрет вебхука настроены заново.
- Искать: разделение ключей по окружениям; не захардкожен ли `sk_test_`/`whsec_`.
- Почти всегда «Требуется моё подтверждение»: Stripe → переключатель Test mode
  выключен → Developers → Webhooks → у live-эндпоинта свой signing secret, и он
  совпадает с переменной на хостинге.

**10. Деньги в целых числах.** Суммы хранятся в минимальных единицах (копейки,
центы) как целые числа.
- Искать: типы столбцов `float`, `real`, `double precision`, `numeric` без масштаба
  для сумм; арифметику `price * 1.2`, `parseFloat`, `toFixed` для денег.
- Пройдено: `integer`/`bigint` с суффиксом `_cents`/`_minor` или аналог.

**11. Двойное нажатие.** Повторное нажатие кнопки оплаты создаёт один заказ.
- Искать: блокировку кнопки во время запроса, ключ идемпотентности
  (`idempotencyKey` в Stripe), уникальное ограничение в БД на заказ/сессию.
- Провал: только `disabled` на фронтенде без серверной защиты — частичный провал.

**12. Налоги.** Налог с продаж/НДС настроен для стран продаж.
- Искать: `automatic_tax: { enabled: true }`, Stripe Tax, налоговые ставки,
  сбор адреса покупателя.
- Панель: Stripe → Settings → Tax — регистрации в нужных странах. Обычно
  «Требуется моё подтверждение».

## Данные

**14. Резервное копирование.** Ежедневные автоматические бэкапы; восстановление
проверено один раз на новой базе.
- На бесплатном тарифе Supabase бэкапов нет: нужен Pro или свой `pg_dump` по
  расписанию (ищи в CI/cron: `.github/workflows`, `pg_dump`).
- Тест восстановления — только в новую тестовую базу, никогда в продакшен.
- Панель: Supabase → Database → Backups.

**15. Миграции с откатом.** У каждой миграции есть SQL отката; миграция и откат
проверены на копии продакшен-данных.
- Искать: `migrations/` — пары up/down или файлы `*_down.sql`/`rollback`.
- Провал: деструктивные миграции (`DROP COLUMN`, `ALTER TYPE`) без отката.
- Прогон на копии продакшена — «Требуется моё подтверждение».

**16. Лимит 1000 строк.** Списки больше 1000 записей не обрезаются молча
(Supabase API по умолчанию отдаёт максимум 1000 строк).
- Искать: `supabase.from(...).select(...)` без `.range()`/пагинации для
  растущих таблиц; подсчёты и экспорты через обычный select.

**17. Время.** Столбцы времени — `timestamptz`; часовой пояс пользователя хранится
отдельно, напоминания идут по местному времени.
- Искать: `timestamp` без `tz`, `date` для моментов времени, `new Date().getHours()`
  на сервере для напоминаний; столбец `timezone` в профиле.

**18. Удаление.** Сначала мягкое удаление (`deleted_at`), RLS скрывает удалённые
записи; удаление аккаунта стирает данные пользователя окончательно.
- Искать: `deleted_at` в схеме и в политиках RLS (`deleted_at is null`);
  обработчик удаления аккаунта — удаляет ли из всех таблиц и из Storage
  (`on delete cascade`, удаление файлов).

**19. Экспорт данных.** Пользователь может выгрузить свои данные.
- Искать: эндпоинт/кнопку экспорта (JSON/CSV), что он отдаёт только данные
  текущего пользователя.

## Работа после запуска

**5. Лимиты расходов.** На всех сервисах с оплатой по использованию (ИИ, SMS,
email) есть лимиты или уведомления.
- Искать в коде: какие платные API вызываются, есть ли rate limiting на
  эндпоинтах, которые их дёргают (иначе любой может сжечь бюджет).
- Сами лимиты — в панелях провайдеров → «Требуется моё подтверждение» со
  списком сервисов и куда зайти в каждом (OpenAI/Anthropic → Billing → Limits,
  Twilio → Usage Triggers, Resend/SendGrid → тариф и алерты, облако → Budgets).

**13. Юридические документы.** Условия использования и политика
конфиденциальности соответствуют реальной работе приложения.
- Искать: страницы `/terms`, `/privacy`; сверить с кодом — какие данные
  собираются, какие сторонние сервисы получают данные (аналитика, ИИ, платежи),
  срок хранения, процедура удаления.
- Провал: документа нет; упомянуты не те сервисы; не упомянута передача данных
  ИИ-провайдеру.

**23. Мониторинг ошибок.** Подключён сервис ошибок (Sentry, Bugsnag, LogRocket,
Highlight и т. п.) на фронтенде и сервере.
- Искать: SDK в зависимостях, инициализацию с DSN из переменной окружения,
  error boundary на фронтенде.
- Панель: что алерты приходят на почту/в мессенджер владельца → «Требуется моё подтверждение».
